# manageapp

Одно Spring Boot-приложение, в котором живут несколько Telegram-ботов (`bots/*`), общий слой Telegram (`common/telegram`), авторизация сайта (`common/auth`), платежи (`payment`) и клиент ИИ-провайдеров с учётом вызовов (`aiconversation`).

## Архитектурные решения

### Выключение ботов: выключенного бота в приложении просто нет

Ботов выключают одной переменной окружения, имена из `BotIdentifier` через запятую:

```
BOTS_DISABLED=HH_BOT,KWORK,AVIA_BOT
```

Пусто — включены все. Опечатка в имени — приложение не стартует, чтобы бот не остался включённым по ошибке.

Боты выключаются по-разному, в зависимости от того, нужны ли они кому-то ещё:

| | Боты | Что происходит при выключении |
|---|---|---|
| **Жёстко** — бота нет в контексте | `ASSISTANT_BOT`, `BOOKING_BOT`, `CHANNEL_POSTER`, `AVIA_BOT`, `HH_BOT`, `KWORK`, `NICOTINE_BOT`, `POMIDORO_BOT` | Spring не создаёт ни одного бина из пакета бота: нет обработчиков, шедулеров, клиентов, контроллеров. Как будто бота не писали. |
| **Мягко** — бот спит | `CALORIE_BOT` (главный продукт), `METRICS` (надзиратель: ошибки и отчёты) | Бины живут, но бот не регистрируется в Telegram и его шедулеры не запускаются. От этих ботов зависят другие модули (channelposter, payment, отправка ошибок), поэтому вырезать их целиком нельзя. |

**Как устроено.**

- `DisabledBotsFilter` — фильтр сканирования компонентов, подключён в `ManageappApplication` через `@ComponentScan`. По пакету класса (`bots.deparrbot.*` → `AVIA_BOT`) решает, пускать ли его в контекст. Сколько и каких ботов вырезано, видно в логе при старте: `Bots excluded from Spring context`.
- `EnabledBots` — мягкое выключение: `TelegramBotsStarter` не регистрирует бота, `BotSchedulerAspect` пропускает `@Scheduled`-методы классов с `@BotScheduler(бот)`.
- JPA-сущности и репозитории сканируются отдельно и остаются даже у вырезанного бота — без его сервисов они ничего не делают, а схема БД не зависит от набора включённых ботов.

**Правило для нового бота.** В «жёсткий» список (`DisabledBotsFilter.BOT_PACKAGES`) попадает только бот, чьи классы никто не импортирует снаружи его пакета. За этим следит `DisabledBotsFilterTest.excludableBotsAreNotImportedFromOutside`: если кто-то начнёт зависеть от такого бота, тест упадёт раньше, чем приложение откажется стартовать в проде.

### Общий `Command` на все боты — осознанно

`common/telegram/Command` — один enum с командами всех ботов: каждая команда хранит свой текст и `BotIdentifier`.

**Как сделали бы по учебнику.** В `common` остаётся только контракт, например `interface BotCommand { String getCommandText(); BotIdentifier getBotIdentifier(); }`, а у каждого бота свой enum. Тогда `common` ничего не знает о конкретных ботах (Dependency Inversion), бот можно вынести в отдельный модуль без правок в ядре, а правка команды одного бота не задевает общий файл.

**Почему оставляем как есть.**

- **Это монолит по замыслу, а не набор будущих микросервисов.** Боты деплоятся одним артефактом, у них общая БД и общий цикл релиза. Граница «бот ↔ ядро» здесь логическая, а не граница развёртывания, поэтому изоляция команд ничего не даёт на практике.
- **Один реестр — единая точка обзора.** По `Command` видно всё, что умеет приложение: сколько ботов, какие у них сценарии, какие служебные команды у платежей и метрик. Если раскидать команды по enum'ам ботов, эта картина пропадёт, и восстанавливать её придётся поиском по проекту.
- **Уникальность и пересечения видны сразу.** Тексты команд, callback-префиксы и «не команды» (`...notcommand`) лежат рядом. Конфликт или дубликат замечаешь при добавлении, а не в рантайме, когда апдейт уходит не в тот хэндлер.
- **Цена связанности маленькая и локальная.** Зависимость однонаправленная: боты читают `Command`, а `Command` знает только `BotIdentifier`. Логики в нём нет, это словарь констант. Конфликты слияния в одном файле для проекта с одним разработчиком не проблема.
- **Путь отхода дешёвый.** Хэндлеры регистрируются по строке (`getHandlerListName()`), поэтому переход на `BotCommand` + enum на бота механический и делается по одному боту. Когда бот действительно понадобится вынести (например, при переезде на telegram-mvc), его команды выносятся вместе с ним.

**Компромисс, который принимаем.** `common` зависит от состава ботов: при добавлении бота меняется ядро (нарушение Open/Closed для этого файла). Чтобы это не расползалось, правило такое: `Command` остаётся чистым реестром констант. Никакой логики, зависящей от конкретного бота, и никаких импортов из `bots/*` в нём нет.
